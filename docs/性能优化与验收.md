# 性能优化与验收（未发布）

本次优化以 Windows、0～10,000 张谱面为边界，保留现有功能、计算算法、媒体质量、Tauri 旧接口和磁盘格式。代码与自动化验证已完成；**真实资料库、原生窗口混合负载及 Linux 验收尚未完成，因此不能宣称整体验收达标或整机提速幅度。**

各行可作为独立审查单元；接口新增需连同 Rust 注册、TypeScript 类型/适配器、Query API 与页面一起回退。当前变更保留在工作区，没有发布或升级版本。既有扫描、PP、技能计算、皮肤工作池和长期音频/渲染线程继续使用原预算；没有增加计算并发或改用无界缓存。

收藏新增 `list_collection_summaries`、`query_collection_entries` 和 `refresh_collection_summaries`。原修改命令已经返回空结果（新建只返回空文件夹），复用其轻量响应，避免再增加等价命令。旧完整快照接口继续兼容。分页键含文件夹修订与偏移；后端拒绝过期修订，前端不混用不同修订，并在修改后失效相关摘要与文件夹分页。

设置修改成功前完成原子替换；收藏常见编辑只复制/序列化选中文件夹，写入失败不发布修改。批量导入、删除、首次旧文件初始化仍使用完整协调路径。保留原状态→缓存以及收藏缓存→文件夹→元数据写入顺序；这不是跨多个文件的事务。旧内联缓存保留到旁路缓存成功落盘，避免延迟初始化覆盖已有数据。派生搜索索引不写入用户文件；其额外内存成本仍需实机量化。

## 测量方法

- 日期：2026-09-19；Windows 11 Home（10.0.26200），Intel Core i7-13650HX，20 个逻辑处理器，约 32 GiB 内存。Rust 1.94.0，Node 22.16.0。
- 参考提交：`d3f2012d867a0ea9ef2ab7933ab577c56b87cbf5`。查询基准在同一 Release 测试进程中交替执行该提交的原查询路径与当前路径，避免两个构建运行时环境波动被当成改进。
- 每条路径先预热 5 次，再交替测量 30 次，单测试线程。表中中位数为排序第 16 个样本，P95 为第 29 个样本；原始摘要见 [performance-2026-09-19.json](./performance-2026-09-19.json)。
- 查询数据为临时目录里的确定性合成索引，每 4 张谱面组成一组。搜索为跨字段 Unicode 多关键词 `测试 group3`，每页 12 项，深分页偏移 2,000。0/1,000 张样本的深分页是越界页，10,000 张样本包含 2,500 个曲包。
- Stable 与 lazer 在各自索引/路径分支执行；lazer 使用合成已解析索引，**没有测真实 Realm 解析、磁盘扫描或完整用户资源读取**。
- 查询对照共享已加载索引，仅测查询调用；完整收藏对照测快照复制与 JSON 序列化，新路径测摘要及第一页构造与序列化。数据字节数不是 WebView IPC 传输耗时，也不含 JSON 协议额外开销。
- 基准未与项目构建/测试同时执行。Windows 调度、杀毒、磁盘路径检测仍可能产生噪声；结果不能外推为启动、渲染或真实资料库吞吐量。

## 复现与采集

先运行构建，再在系统负载稳定时单独运行基准：

```powershell
cargo test --manifest-path src-tauri/Cargo.toml --release performance_ -- --ignored --nocapture --test-threads=1
pnpm build
node scripts/measure-bundle.mjs
```

入口脚本递归累计 manifest 中静态 imports 和 CSS，并按每个入口去重，同时报告原始字节和逐文件 gzip 之和。主窗口与迷你播放器必须一起比较；不包含 HTML、动态路由、运行时图片/字体，因此只是首屏依赖下界，完整首次页面加载仍需网络面板或跟踪确认。基线使用参考提交的独立副本，只启用 Vite manifest 后构建，未修改其生产源码。

可选前端观测：在测试用 WebView 的开发工具中执行 `localStorage.setItem("opp:performance", "1")` 后重启，读取 `window.oppPerformance.snapshot()`；`reset()` 清空记录。关闭为删除该 localStorage 项后重启。默认关闭，最多保留 2,048 条，只记录命令名、耗时、响应 JSON 字节数及长任务，不保留参数、响应内容、身份或凭据。覆盖统一 Tauri/音乐适配器，绕过适配器的直接调用不在其统计范围。序列化测量本身有开销，比较时必须保持同样的开关状态。

`frontend_interactive` 从 WebView navigation time origin 计时到身份门就绪，**不等于进程创建至所有页面可交互**。结合后端 `app.lifecycle / initialize_services` span 和外部进程启动时间，分别记录各阶段，不能直接相加异步重叠时段。未提供原生 Release WebView 的自动导出通道，开发工具不可用时须用独立测试构建或外部跟踪采集。

进程树采样（输出到独立测试目录，根 PID 必须为本次 OPP）：

```powershell
./scripts/measure-process.ps1 -RootProcessId 12345 -Seconds 120 -OutputPath C:/Temp/opp-process.json
```

CPU 为相邻采样的进程树 CPU 秒增量；私有内存和工作集为当前树求和，工作集可能重复计入共享页。PID 与启动时间一起识别进程，根退出时停止。采样间已退出的短进程可能漏计，外部渲染器需单独记录总耗时，不能将其速度算作 OPP 查询改进。

任务日志的 `queue_ms` 与完成 span 的 `duration_ms` 分别用于排队、执行；外部 CollectionManager/danser/FFmpeg 的运行时间应单列。日志队列容量 1,024，批次 64 条或空闲 250ms 刷新；错误立即刷新，过载普通日志聚合计数，严重日志有应急 JSONL 输出，正常退出等待排空。用户态缓冲刷新不代表 fsync，强制结束进程不在排空保证内。

仍待独立 Windows 验收：

1. 使用空库、1,000/10,000 张 Stable/lazer 真实独立副本和大型收藏，固定电源策略、客户端版本、资料库快照、操作顺序；不得使用用户原文件作为写入样本。
2. 启动分别测试应用缓存空/热，各至少 5 次，从进程创建记录至首屏实际可交互；应用缓存空不代表操作系统冷缓存。扫描、渲染等长任务各至少 5 次。
3. 搜索、翻页预热后各至少 30 次，记录中位数/P95、长任务、IPC、任务排队、进程树 CPU、峰值私有内存；图片首取/命中分开。
4. 扫描时搜索和切歌、下载时翻页、渲染时修改设置；反复快速切页、隐藏/恢复、主窗口/迷你播放器切换与任务取消，持续观察内存和重复请求。
5. 比较至少两轮稳定结果：确认热点至少改善 20%，其他关键耗时与峰值内存无超过 10% 的可重复退化。没有数据的项目保持“未验证”，不能由单元测试或本报告的查询基准判为通过。

Linux 编译与运行、真实相似数据集、音频设备/游戏监测/原生渲染与外部程序均未完成本轮实机验证。入口体积仅小幅变化；启动、峰值内存和混合负载缺少前后数据，是当前剩余验收工作。
