# OPP 后端代码组织方式

本文规定 OPP Rust 后端的代码组织、依赖方向和模块边界。目标不是让每个功能拥有相同数量的文件，而是让领域语义、业务流程和外部实现彼此隔离。

## 模块基本结构

一个较完整的业务模块推荐组织为：

```text
<module>/
├── models.rs
├── ports.rs
├── adapters/
│   ├── mod.rs
│   └── xxx.rs
├── service.rs
├── commands.rs
└── mod.rs
```

依赖方向如下：

```text
models
   ↓
ports
   ↑
adapters

models + ports
      ↓
   service
      ↓
   commands
```

- `models`：定义 OPP 自己理解的数据语义。
- `ports`：定义业务需要的能力，不指定具体实现。
- `adapters`：连接文件、网络、数据库、操作系统和第三方程序。
- `service`：编排真正的业务流程。
- `commands`：将 service 暴露为 Tauri command。
- `mod.rs`：声明内部模块并控制对外公开的边界。

## models：统一数据语义

`models.rs` 定义 OPP 自己的领域数据，而不是复制外部软件的数据结构。Stable、lazer、Realm、HTTP 响应或平台 API 的原始结构应在 adapter 中完成转换，不能继续泄漏到 service 和 command 契约。

跨 feature 共享且语义稳定的模型放在 `src-tauri/src/domain/`。只属于单个 feature 的请求、响应和运行态保留在该 feature 的 `models.rs`。

## ports：定义能力

`ports.rs` 用 trait 或清晰的接口定义模块依赖的外部能力。只有在存在多实现、需要替换、需要测试替身或外部差异明显时才创建 port；单一且简单的实现不必为了目录完整而增加抽象。

## adapters：隔离外部世界

Adapter 内允许出现：

- 文件路径和磁盘格式；
- JSON、HTTP 和第三方 API；
- Realm、Stable 与 lazer 数据结构；
- Windows/Linux 平台 API；
- 第三方程序的命令行和进程协议。

Adapter 的职责是将这些外部细节转换为 OPP 模型或 port 能力。业务 service 不应判断数据来自 Stable、lazer、API 还是操作系统。

仓库级公共适配位于 `src-tauri/src/infrastructure/`；只服务于单个 feature 的适配可以放在该 feature 内的 `adapters/`，或在实现仍很简单时使用职责明确的单文件模块。

## service：业务流程

`service.rs` 决定操作顺序、数据处理、错误语义和多个能力的组合。Service 不应关心：

- Tauri command 如何声明；
- HTTP 客户端如何构造；
- Windows/Linux 程序如何启动；
- Stable 与 lazer 的原始存储差异。

大型 service 可以按职责拆成 `service_query.rs`、`service_data.rs` 等内部文件，但不能只按行数机械拆分。

## commands：薄前端入口

Tauri command 只负责：

- 参数反序列化和必要的边界校验；
- 从 `AppState` 获取依赖；
- 调用 service；
- 将错误和结果转换为前端契约。

判断标准：删除 `#[tauri::command]` 后，如果剩余代码仍是一段完整业务流程，该流程应进入 service。所有 command 在 crate 根部的 `commands.rs` 统一注册，前端 command 名在内部重构时保持稳定。

## mod.rs：控制公开边界

`mod.rs` 应保持简短，只声明内部模块并公开其他模块确实需要的类型、service 或 command。Adapter、解析器和内部辅助类型默认私有；不要使用宽泛重导出来掩盖实际依赖方向。

## 按复杂度选择结构

小工具适合单文件：

```text
tools/
├── bpm.rs
├── key_speed.rs
└── path.rs
```

适用条件是功能单一、没有复杂状态、没有多个外部数据源，也没有独立领域模型。

中型功能可以只包含必要文件：

```text
skin/
├── models.rs
├── service.rs
└── mod.rs
```

大型功能在出现多数据源、多平台、多实现、大量业务处理或跨功能复用时，应形成完整的 models/ports/adapters/service/commands 边界。

## Rust 后端总体结构

当前仓库结构为：

```text
src-tauri/src/
├── domain/                 # OPP 认识什么
│   ├── defaults.rs
│   ├── models.rs
│   └── mod.rs
├── features/               # OPP 能做什么
│   ├── account/
│   ├── beatmaphub/
│   ├── collections/
│   ├── local_analysis/
│   ├── online_beatmaps/
│   ├── similarity/
│   ├── skin_workshop/
│   └── ...
├── infrastructure/         # OPP 如何连接外部世界
│   ├── osu_api.rs
│   ├── platform.rs
│   ├── portable_update.rs
│   ├── storage.rs
│   └── mod.rs
├── tools/                  # 独立小工具
├── state.rs                # 依赖装配和共享运行态
├── commands.rs             # Tauri command 注册表
├── error.rs                # 统一错误契约
├── lib.rs                  # 应用启动与生命周期
└── main.rs                 # 二进制入口
```

顶层依赖方向是：

```text
commands / application startup
             ↓
          features
          ↓      ↓
       domain   ports
                  ↑
          adapters / infrastructure
```

`domain` 不依赖 feature 或 infrastructure。Feature 可以依赖 domain，并通过明确接口使用 infrastructure；infrastructure 负责外部结构转换，不承载业务流程。跨 feature 调用必须使用 `crate::features::<name>` 显式路径，不能在 crate 根部创建兼容别名来隐藏依赖。

## 最终规则

1. Model 统一数据语义。
2. Port 定义能力，不定义具体实现。
3. Adapter 隔离 Stable、lazer、API、tosu 和平台差异。
4. Service 负责业务逻辑与流程组合。
5. Command 只负责把 service 暴露给前端。
6. `mod.rs` 控制模块边界，内部实现默认私有。
7. 简单功能保持简单，不为了架构而架构。
8. 模块按职责拆分，不机械按照文件行数拆分。
9. 重构不能改变现有 Tauri command 名和序列化契约，除非同时完成前端迁移与兼容说明。
