# OPP 问题排查实录

本文件记录值得留存的排查与修复过程：现象、定位思路、根因与修复策略。
它与[版本变更记录](./版本变更记录.md)的分工是——**版本记录只写"改了什么、用户可感知什么"，本文件写"怎么定位的、为什么这样修"**，供后续维护者遇到同类问题时参考。

新增条目约定：按时间倒序排列；标题带日期；涉及外部系统（osu! 客户端、镜像站、Realm 等）的行为结论需注明"实测"；不要抄入用户个人数据。

## 2026-11 · collection.db 写入成功但游戏内收藏夹整批消失

**现象**：「导入 Stable」显示成功，谱面也都在游戏里，但新增收藏夹（含比赛图池夹）在 osu!stable 内始终不出现；退出重进多次无效，OPP 重写后再次进游戏又被清掉，形成死循环。

**定位过程**：

1. OPP 日志显示写回命令没有报错，且 `collection.db.bak`（OPP 写回时的旧文件备份）确实包含全部 14 个收藏夹——写入侧成功。
2. 字节级比对：OPP 写出的文件与 osu! 自己写的版本中 10 个同名收藏夹**逐字节一致**（ULEB128、字符串标记、版本号全同），谱面 MD5 也全部存在于 `osu!.db`——编码与数据都没问题，排除"写错格式"。
3. osu! 目录下有它自己生成的 `collection.db.<.NET ticks>.bak` 时间戳备份，串出时间线：**每次 OPP 写入 9413 字节（14 夹）→ osu! 下次启动后退出时重写为 7479 字节（10 夹）**，六次循环全部如此；而 osu! 只在收藏夹"脏"时才重写 collection.db（无变化的一个会话后文件 mtime 不变），说明它在**读取时**就改动了内容。
4. 对比保留/丢弃的集合：osu! 恰好保留了 OPP 文件中重复名称出现**之前**的全部条目——OPP 内部状态里有两个同名 `test`（游戏原有 3 图夹 + 用户在 OPP 新建的同名 1 图夹）。

**根因**：osu!stable（20260924 实测）按名称索引收藏夹，加载 collection.db 遇到重名条目时在该条目处中断解析，**该项及其后的所有收藏夹全部丢弃**，退出时把截断结果排序写回。与谱面是否已导入无关。

**修复策略**（防御分层）：

- 写回兜底：`stable_db_for_write` 把同名文件夹合并为单个收藏夹（MD5 并集去重、保留首次出现顺序）——无论内部状态如何产生重名，都不会写给游戏；
- 源头校验：创建/重命名收藏夹时拒绝与"参与 Stable 同步的收藏夹"重名（lazer 只读镜像不参与写回，不受限）；
- 体验闭环：「补齐并写回 Stable」遇 `COLLECTION_CONFLICT` 自动"读取 Stable 合并后重试一次"——因为 osu! 每次退出都可能重写 collection.db，指纹过期是常态而非异常，不应要求用户手动刷新。

**教训**：外部系统"读取时静默修正数据"比"写入失败"更难察觉——写入成功≠被接受。字节级 diff（同一份数据两种来源的编码对比）是排除自身编码问题的最快手段。

## 2026-11 · osu! 退出时覆写收藏夹，OPP 写入被抹掉

**现象**：OPP 写入 collection.db 后，用户进过一次游戏，OPP 的收藏夹分组就消失了。

**定位**：osu!stable 在退出时用**启动时的内存快照**整体回写 collection.db——进程生命周期内磁盘上的任何外部修改都会被覆盖。这与上一条不同：那个是"读时丢弃"，这个是"退出覆写"。

**修复策略**：全局写回监视器（`StableWriteBackWatcher`）监听游戏进程退出，延迟数秒（等游戏完全落盘）后：检测到游戏侧变更先执行"读取 Stable"把游戏当前收藏合并进 OPP（游戏内新增导入、删除尊重、OPP 自建夹保留），再整体写回；OPP 启动时若 stable 未运行也做一次同样的收尾自愈。写回失败不再静默，以任务失败提示重试。

**教训**：对"退出时回写"类外部系统，正确的同步模型是**事件驱动的读合并 + 写**，而不是单向写。

## 2026-11 · 令牌刷新撞上 osu! 瞬时 500，用户被强制登出

**现象**：重新编译后应用反复停在授权页。日志显示 `refresh_token` 收到 osu! 500 后本地令牌被清空，一切请求变成 `AUTH_REQUIRED`；重登时浏览器授权页又因当时到 osu.ppy.sh 的链路不稳而打不开，表现为"一直卡授权"。

**定位**：`ensure_access_token` 的旧逻辑对**任何**刷新失败（网络超时、5xx、429）都清空令牌强制重登。瞬态故障被当成凭据失效处理，把用户踢进一个当时根本无法完成的浏览器流程。

**修复策略**：按错误码分层——只有服务端明确拒绝刷新令牌（`TOKEN_REFRESH_FAILED` 即 400 invalid_grant、`AUTH_REQUIRED` 即 401）才清凭据；网络/服务端瞬时错误保留令牌，下次请求自动重试刷新。错误码映射集中在 `osu_api.rs::map_status`。

**附**（授权链路排障清单）：回调监听固定在 `127.0.0.1:42831`（占用立即报 `CALLBACK_PORT_OCCUPIED`）；state 不匹配的回调会被回复浏览器后静默忽略、继续等待——重试前应关闭旧授权标签页；浏览器点授权后若显示"无法访问 127.0.0.1"，先检查代理是否绕过回环地址；排查"卡授权"先看 OPP 日志的 `refresh_token`/`授权已取消` 再 curl 探 osu.ppy.sh 主页与 `/oauth/authorize` 的连通性。

## 2026-11 · 在线谱面页大面积"本地状态未知"，重扫无效

**现象**：在线谱面页几乎所有谱面显示"本地状态未知"，重新扫描本地谱面后依旧。

**定位**：本地存在性查询（`beatmap_presence`）的信任判定把"扫描出现过**任何**逐文件诊断（`BEATMAP_PARSE_ERROR` 等）"视作整个索引不可信，未命中一律返回 Unknown。实测用户 lazer 库有恰好 1 个无可识别 HitObject 的损坏谱面——一个坏文件毒化了两个客户端全部 1.3 万条目的判定，且该文件固定存在，重扫永远无法消除。

**修复策略**：判定粒度对齐故障粒度——逐文件诊断只影响该文件自身条目（那张图本来就打不开，顶多它一张被误报"未收录"）；全局信任只由扫描完整性（complete/partial）、扫描阶段（pending/scanning/error）、来源在线状态与来源路径一致性决定。

**教训**：保守判定（"不确定就 Unknown"）的**粒度**要和不确定性来源匹配，否则一个局部故障会放大成全局不可用。

## 2026-11 · 2014 前老谱面在所有镜像上"下载失败"

**现象**：比赛图池补齐时，DT/HR 老图大面积报"镜像返回的谱面文件与所选谱面集不符"，换镜像也无效。

**定位**：压缩包校验要求 `.osu` 的 `BeatmapID`/`BeatmapSetID` 与所选谱面集一致，一票否决。2014 年前的经典老图元数据里**根本没有 ID 字段**（或为 0/-1 未提交难度），校验必然失败——不是镜像串包，是我们把"无法验证"当成了"验证失败"。

**修复策略**：无 ID 难度按**归一化标题**兜底校验（只保留字母数字小写比对，ASCII/Unicode 任一命中即可），仍能拦截镜像返回完全不同曲目的真串包；混入带错误集合 ID 的难度文件依旧整体拒绝。收藏条目回填同理增加（标题, 难度名）→ 标题两级回退，老图 MD5 能正确写进 collection.db。

## 2026-10 · OTD 进程"检测不到运行"，无论选哪个可执行文件

**现象**：选择 `OpenTabletDriver.Daemon.exe` 后进程状态恒为未运行，OTD 明明开着。

**定位**：Windows `tasklist` 表格输出的镜像名列**固定 25 字符宽**，超长进程名被截断（`OpenTabletDriver.Daemon.exe` → `OpenTabletDriver.Daemon.`），子串匹配永远失败。

**修复策略**：改用 `tasklist /FO CSV` 输出完整进程名后再匹配。同类教训：解析命令行工具的"人类可读"表格输出前，先确认列宽是否固定。

## 2026-10 · 后端命令写入的路径，被前端"整份设置回写"覆盖回 null

**现象**：OTD / tosu / tosu 歌词代理路径选择成功后，再次打开设置页变回空。

**定位**：这些路径由后端命令直接写设置文件，但设置页等处的保存流程是"前端缓存快照 → 整份回写"，用的是**旧快照**，把后端刚写入的路径覆盖回 `null`。

**修复策略**：选择路径后立即同步前端设置缓存；设置查询不再永久缓存（挂载时重新拉取）。同类双写入口都要遵守：**后端写、前端读后写**的路径必须共用同一份新鲜状态。

## 2026-10 · lazer 索引重启后报 `invalid type: null, expected f64`

**现象**：lazer 本地扫描正常，重启应用后恢复索引报反序列化错误，需要重新扫描。

**定位**：个别谱面缺少 TimingPoint 时 rosu-pp 把 BPM 算成 `Infinity`，serde_json 序列化为 `null` 落进索引库；`null` 与 `f64` 类型不符，重启恢复时整库解析失败。

**修复策略**：入库前把所有非有限浮点收敛为有限值；恢复时遇到历史损坏条目跳过该条、记录诊断并立即回写数据库自愈（被跳过的谱面重新扫描后恢复）。同类教训：**边界值（NaN/Infinity）落库前必须收敛**，否则会变成持久化的定时炸弹。
