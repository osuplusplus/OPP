# OPP 架构与开发

本文档集中维护环境准备、模块边界、质量检查与发布流程。用户操作见[项目 README](../README.md)，专题说明见[文档中心](./README.md)。

PR 请提交到 **dev** 分支；问题与方案讨论使用仓库 Issues。

## 环境与命令

- Node.js 22+、pnpm 11+、Rust stable。
- Windows：MSVC 工具链、Windows SDK 与 WebView2 Runtime。
- Linux：系统包、客户端命令和桌面依赖见 [Linux 使用与构建](./Linux.md)。

```bash
pnpm install
pnpm tauri dev
```

`pnpm dev` 仅运行 Vite 前端；需要本地文件、凭据或游戏能力时使用 Tauri 开发环境。`pnpm test:watch` 用于持续运行前端测试。


## 技术结构

OPP 由 Tauri 2 承载 React 19 前端与 Rust 后端，支持 Windows x64 与 Linux。后端通过平台适配层隔离两套系统的进程、路径和凭据差异：

```text
React 页面与组件
  → features/*/api.ts（TanStack Query 状态边界）
  → shared/lib/tauri.ts（类型化命令适配层）
  → Tauri command
  → Rust 领域模块
  → osu! API、本地文件、系统凭据或外部应用
```

前端不直接访问本地文件和凭据；Rust command 负责输入校验、权限边界与错误转换。远端响应和本地索引数据通过 `shared/types/osu.ts` 中的序列化契约传递。

## 前端边界

- `src/app/`：应用壳、路由、侧栏、标题栏和全局客户端/模式上下文。
- `src/features/`：按业务域组织页面、查询适配、局部组件和纯逻辑。跨域调用应通过公开 API 或小型共享事件，不应导入另一个页面的内部状态。
- `src/shared/components/`：无业务状态的可复用组件。
- `src/shared/lib/`：格式化、样式合并和 Tauri 命令适配。
- `src/shared/types/`：前后端共享的数据契约。

大型页面应把纯筛选/转换逻辑放入同目录的模型文件，把独立视觉区域拆成组件；副作用只用于外部同步、订阅和资源释放，不用于镜像可推导状态。

## 后端边界

Rust 后端按 `domain / features / infrastructure` 组织。详细规则见[后端代码组织方式](./后端代码组织方式.md)。

- `domain/`：跨功能共享且语义稳定的 OPP 模型与默认值，不依赖 feature 或外部实现。
- `features/`：面向用户的业务能力。复杂模块使用 `models.rs`、`service.rs`、`commands.rs` 和内部适配文件；`mod.rs` 只声明模块与控制导出。
- `infrastructure/`：osu! API、平台探测、持久化和便携更新执行等仓库级外部适配。
- `tools/`：没有复杂状态或独立领域模型的单一工具。
- `state.rs`：装配 service、adapter 和共享运行态。
- `commands.rs`：集中注册全部 Tauri command，内部重构不能改变前端 command 名。
- `lib.rs`：只负责 Tauri 插件、共享状态、后台监控器、托盘和应用生命周期。

主要 feature 包括：

- `features/account/`：OAuth 回调、Token 刷新、系统凭据和账号缓存。
- `features/collections/`：Stable/lazer 收藏夹读取、分享码、缺失谱面补齐和安全写回。
- `features/danser/`：Danser/ffmpeg 探测、本地渲染参数、任务队列和进度事件。
- `features/local_analysis/`：Stable/lazer 来源识别、解析、增量索引、查询和本地资源预览。
- `features/skin_workshop/`：Stable Skin、临时 `.osk` 包、组件暂存、融合预览和原子写入。
- `features/online_beatmaps/`：官方查询参数、镜像提供方和下载队列。
- `features/update.rs` 与 `infrastructure/portable_update.rs`：版本检查、更新包下载、Windows 便携 EXE 原路径替换、重启和早期失败回滚。
- `features/similarity/`：按 ruleset 隔离的 Standard Analyzer v4 / Mania v4 运行包及旧格式兼容校验、输入来源、查询模型和个性化推荐。
- `features/replay_render/`、`features/tosu/`、`tools/`：在线渲染、直播工作流、谱面预览和 lazer 空间工具。
- `features/live_render/`：依赖 Git 版本的 `osu_replay_render`，负责实时回放预览与 FFmpeg 视频导出。Windows 和 Linux/X11 使用原生 GPU 窗口；播放、选项与导出通过命令和事件同步。FFmpeg 优先读取手动配置，其次 PATH 和 Danser 发行包。
- `features/music_player/`、`features/tournament_pools/`、`features/beatmaphub/`：本地音频播放、图池 URI 导入与社区曲包工作流。
- `infrastructure/platform.rs`：进程启动、路径打开和平台能力探测。
- `error.rs`、`state.rs`、`infrastructure/storage.rs`：统一错误、运行态和持久化基础设施。

Rust 领域函数返回结构化错误；Tauri command 保持薄层，只完成状态获取、参数校验和服务调用。任何磁盘写入都应明确目标目录，临时产物应可清理或原子替换。

## 本地状态与敏感数据

- OAuth Client Secret、Token 和 OBS 密码保存在系统凭据服务（Windows Credential Manager 或 Linux Secret Service）。
- 设置、缓存和扫描索引保存在应用数据目录，不进入源码仓库。
- 相似谱面数据集只读访问用户选择的目录，不随 EXE 分发。
- 回放仅在用户主动提交渲染时发送到 o!rdr。

## 平台边界

- Windows 从注册表和用户目录探测客户端，Linux 从 XDG 数据目录探测，并通过 PATH 中的 `osu-wine` / `osu-lazer` 启动游戏。
- Windows 使用 Credential Manager；Linux 使用基于 D-Bus 的 Secret Service。
- Linux 通过 `/proc` 检测 osu!、OBS 与 tosu 进程；tosu 需要 `pkexec` 完成读取 Wine 进程所需的授权。
- 文件关联和显示器伽马依赖 Windows API，只在 Windows 前端能力开关启用。
- Danser 在 Windows 使用 `danser-cli.exe`，Linux 使用 PATH 中的 `danser` 和 XDG 配置目录；两端渲染均需要 FFmpeg。
- 平台相关业务应统一进入 `platform.rs` 或能力开关，避免在页面和领域模块中分散操作系统判断。

## 任务与日志

重任务通过 `src-tauri/src/infrastructure/tasks.rs` 调度：交互查询使用 `interactive`，批量计算使用 `background`，同步外部 I/O 使用 `blocking_io`。音频、渲染和文件监听由各自常驻线程负责。不要在 UI／Tokio 工作线程中执行长时间同步计算，也不要持有业务锁等待工作池。扫描和下载等长任务仍需显式协作取消。

Tauri 命令、文件／网络／数据库／凭据操作、外部进程、错误路径及关键流程应使用 `infrastructure::logging` 记录结构化日志，通过 `LogSpan` 或 `finish_span` 保留结果和耗时。JSONL 日志位于应用数据目录的 `logs/`，由后台有界队列写入并轮转，敏感字段需脱敏。不要把凭据、应用数据或诊断导出提交到仓库。

## 质量门槛

提交前在目标平台运行：

```bash
pnpm lint
pnpm test
pnpm build
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --all-targets
```

Windows 与 Linux 必须分别构建和实机验证。单元测试或交叉编译不能代替音频、真实游戏数据库、原生窗口、URI 唤醒及便携更新验收；图池专项场景见 [OPP URI 标准](./OPP-URI标准.md#6-平台接口与验收)。

## 发布流程

1. 同步更新 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 的 OPP 包版本及 `src-tauri/tauri.conf.json`，更新 README 版本徽标。前端“关于”页在构建时读取 `package.json`。
2. 将最终用户可见变化整理到[版本变更记录](./版本变更记录.md)中对应的 `## vX.Y.Z` 段落，合并同版本的重复迭代描述。
3. 执行上述质量检查，并用 `node scripts/prepare-release.mjs v0.5.0` 校验四处版本与目标 tag 一致、生成该版本的 Release 正文（发布其他版本时替换参数）。
4. 在对应平台执行 `pnpm tauri build` 并完成实机验收。仓库默认 `bundle.active: false`，主程序位于 `src-tauri/target/release/opp.exe` 或 `opp`；安装包需显式选择 `--bundles nsis`，Linux 打包见平台文档。
5. 将准备好的提交标记为 `vX.Y.Z` 后推送 tag，或在 GitHub Actions 中手动运行 [Release 工作流](../.github/workflows/Release.yml)，选择包含发布代码的分支并填写版本 tag。手动发布不要求 tag 预先存在。工作流固定检出触发时的提交，在构建前校验版本和读取发布说明；新 Release 的 tag 指向同一提交。已有 tag 的补构建应从原 tag 运行，避免将其他提交的产物上传到该版本。
6. 工作流构建 Windows 便携 EXE、NSIS 安装包及 Linux AppImage／deb，上传 `latest.json`。所有矩阵任务成功前 Release 保持 Draft，最后统一发布；若任务失败，修复或重跑并核对资源完整性。

准备版本号和文档本身不会触发发布；推送 tag 或手动运行工作流会在全部构建成功后自动公开 Release。

### Windows 便携更新

客户端固定读取 `https://github.com/osuplusplus/OPP/releases/latest/download/latest.json`。工作流按实际上传的便携 EXE 文件名生成清单：

```json
{
  "version": "0.5.0",
  "url": "https://github.com/osuplusplus/OPP/releases/download/v0.5.0/OPP_0.5.0_windows_x64_portable.exe"
}
```

发现更高版本后，客户端从清单 HTTPS 地址下载 EXE。当前程序的临时副本等待旧进程退出，替换原路径文件并重启；新版本启动早期异常退出时恢复旧 EXE。首个带更新器的版本需手动下载一次，目录不可写或不是 Windows x64 时可前往 Release 页下载。
