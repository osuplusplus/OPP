# 线程与任务调度

## 执行边界

| 执行环境 | 负责什么 | 不应放入什么 |
| --- | --- | --- |
| WebView UI 线程 | React、输入、绘制、接收小型结果 | 全库遍历、大量同步计算、连续提交过期查询 |
| Tauri 主线程 | 原生窗口操作、极短的状态读取或发送控制消息 | 文件扫描、图片解码、压缩包读取、等待外部进程 |
| Tokio 异步运行时 | HTTP、WebSocket、异步等待、任务编排 | 同步解析、图片处理、长时间持锁、同步进程等待 |
| `tasks::interactive` | 本地分页查询、详情、封面、单谱 PP、播放队列构建 | 全库扫描、批量导出、常驻循环 |
| `tasks::background` | 扫描、相似度计算、技能分析、查重、转换、预览生成、压缩包导入导出 | 音频播放、实时渲染、窗口操作 |
| `tasks::blocking_io` | FFmpeg/NVENC 探测、Danser 状态与配置枚举、预览文件读写 | 计算密集的批处理、常驻循环 |
| 专用常驻线程 | 音频核心、原生渲染、文件监听、日志写入、外部渲染进程队列 | 无关的临时计算 |

`#[tauri::command(async)]` 只改变命令的调度位置，不会把函数里的同步工作自动变成非阻塞操作。计算和同步 I/O 必须显式交给工作池。参见 [Tauri 命令文档](https://v2.tauri.app/develop/calling-rust/) 和 [Tokio spawn_blocking 文档](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)。

## 线程预算

调度入口位于 `src-tauri/src/infrastructure/tasks.rs`。三个线程池均在进程内共享，按需初始化，线程名称分别为 `opp-interactive-*`、`opp-background-*`、`opp-blocking-io-*`。

| 可用逻辑 CPU | 交互工作线程 | 后台计算线程 | 阻塞 I/O 线程上限 |
| --- | --- | --- | --- |
| 1～2 | 1 | 1 | 2 |
| 3 | 1 | 1 | 2 |
| 4 | 1 | 2 | 2 |
| 5 及以上 | 1 | 3 | 2 |

这是应用重任务池的预算，不是进程总线程数或 CPU 亲和性限制。Tokio、WebView、音频、GPU 驱动和外部 FFmpeg 仍有自己的线程。单/双核机器无法在同时运行 UI 与计算时保证空闲核心；这里优先减少竞争，允许批处理总耗时增加。

每个异步工作池最多保留 128 个已提交任务（含执行中的任务）；超限返回可重试的任务繁忙错误，不无限增加线程和队列。Rayon `par_iter` 在当前共享池内执行，扫描和查重不会各自再占用一套全核工作线程。任务异常通过错误返回，避免 Rayon 的未处理 panic 终止进程。

## 接入方式

异步命令先复制必要的参数或 `Arc`，再等待工作池：

```rust
let service = state.local_analysis.clone();
crate::infrastructure::tasks::interactive("query_local_beatmaps", move || {
    service.query_beatmaps(query)
}).await?
```

不要把网络下载连同计算一起塞进闭包：先异步下载，再将字节交给工作池。不要在 UI 或 Tokio 上调用同步 `install`；它会阻塞调用线程。不要持有业务锁跨工作池等待，否则可能导致锁竞争或死锁。

本地扫描保留一个特殊入口：在同步后台编排线程中先登记客户端扫描和取消标记，再通过共享后台池 `install` 执行完整扫描。这使得排队扫描也能接收取消；同一客户端重复请求仍立即返回 `SCAN_IN_PROGRESS`。文件监听和收藏刷新调用同一个扫描入口，同样受到计算预算约束。

## 取消、事件与 UI 压力

- 调度层在开始执行前检查接收端是否已关闭。Rust 调用方丢弃等待 future 时，尚未执行的工作会跳过；已经开始的工作不被强行中断。
- 这不等于浏览器侧取消 IPC。页面卸载或 TanStack Query 取消不会自动停止已发出的 Tauri 命令。扫描与查重仍使用各自显式的协作取消标记。
- 查重在入队前登记单任务状态并重置取消标记，执行开始时不再清除取消，避免排队期间的取消失效。任务完成、失败或闭包被丢弃时释放登记状态。
- 文件监听只保留一个“目录发生变化”的通知；`try_send` 不阻塞系统监听回调。去抖等待最多约一秒，连续写入不会让扫描永久等待静默。扫描期间的新事件保留为下一轮增量扫描。
- 本地谱面搜索和皮肤搜索使用 200ms 去抖；输入更新立即呈现，昂贵的 IPC 查询等输入稳定后再发送。React `useDeferredValue` 本身不会限制请求频率。
- 缓存加载发布索引后立即释放写锁，再清理缩略图磁盘缓存，避免文件遍历占着索引锁。

## 验证与诊断

### 页面切换的专项处理

切换卡顿不只有线程数量问题，还包括前端单次挂载规模、缓存失效范围以及主线程上的同步命令：

- 收藏夹原来默认展开所有文件夹并挂载每个谱面的卡片。现在每页 6 个文件夹，每个文件夹每页 12 张卡片；导入预览每页 50 项。其余条目通过分页访问，不再同时产生 DOM、图片请求和布局计算。底层收藏夹快照仍保持现有完整数据协议，未改成后端分页。
- AppShell 常驻的收藏弹窗仅在打开时启用查询。收藏页探测缺失项后显示提示，由用户点击现有补齐按钮处理，不再弹出阻塞 WebView 的 `window.confirm`。
- 懒加载的 Suspense 边界位于页面内容区域，按路由路径重置，加载新页面时保留侧栏与全局控件；旧页面仍在等待加载时，也能离开并打开另一页。模式和客户端状态使用 React transition，使后续交互可以打断未完成的页面渲染。
- 本地索引的变化在 QueryClient 生命周期内比较；重复挂载和模式切换不等于索引更新。只有加载完成、扫描修订变化或用户修改资源时才按客户端失效缓存，非活动查询只标记过期；完整谱面集缓存也在这一范围内。
- 在线检索避免因为重新挂载或窗口重新获得焦点而自动重取所有已缓存分页，主动搜索与重试继续可用。
- 本地页只订阅当前播放曲目的资源 ID，播放器进度 tick 不再触发整个本地页面重绘。
- 读取设置使用小型内存快照，已初始化的设置不再触发全缓存淘汰与序列化；首次补全默认下载目录仍按原约定持久化。身份、资料与成绩缓存读取只复制所需字段。身份/设置读取、设置修改、首次页面引导记录和收藏状态查询在工作线程中执行。

新增回归测试使用含 2,000 项的收藏夹确认只挂载当前 12 张卡片，检查分页可达性、数据减少后的页码修正、关闭弹窗不查询、索引修订不变时不刷新、Stable 更新不影响 lazer、播放进度不重绘导航，以及页面包未加载完成时仍可通过侧栏离开。

### 实机验收

调度日志以 `tasks` 为 target，记录排队时间 `queue_ms`、工作线程名，以及已有操作 span 的执行耗时。该 span 表示工作闭包是否正常返回；业务错误继续通过原有 `CommandError` 和业务 span 记录。可据此区分队列拥堵、计算慢和 I/O 慢。

自动测试覆盖线程预算、嵌套并行计算复用工作池、panic 后继续执行、排队任务取消与容量释放、繁忙拒绝、后台饱和时交互任务及 Tokio 仍可运行；前端测试覆盖搜索去抖和卸载清理。

低配实机验收建议使用同一份 Stable/lazer 数据与相同缓存状态，比较修改前后：

1. 全量扫描期间连续搜索、打开详情、切歌，记录输入延迟和调度日志中的排队时间。
2. 同时启动查重与扫描，观察 CPU、线程数、峰值内存及 UI 长帧；同时记录扫描总耗时，避免只比较吞吐量。
3. 导入大量文件，确认事件队列不会持续增长，变化最终进入索引，取消后能够再次启动任务。
4. 打开渲染设置进行 FFmpeg/NVENC 检测，确认窗口仍能拖动和响应。
5. Windows 与 Linux 分别验收。单元测试不能替代原生窗口、音频、第三方渲染和实际磁盘负载下的测量。

当前接入覆盖上述主要重任务入口。启动时 `AppState::new` 的同步状态恢复、其余短同步设置/凭据命令、第三方库或外部程序内部线程仍沿用原有实现；这里没有把所有线程强制纳入同一个线程池，也没有测得低配实机上的提速百分比。


## 后续性能优化

收藏文件和响应缓存改为首次使用时恢复，读取或修改前必须完成同一次初始化；失败不会发布空收藏，后续请求可以重试。资料、成绩和技能分析缓存的读取与写入交给 `blocking_io`；设置读取直接访问小型内存快照，设置写入不加载响应缓存。收藏常见编辑和分页命令也显式进入工作池。

相似数据集使用按目录与配置代次隔离的加载槽。清理只移除槽的登记，不等待磁盘加载；旧任务可以完成自己的请求，但不能覆盖新代次。在线封面维持一个网络请求并发量和最多 128 个待处理加载；同资源请求共享结果，本地封面按客户端、资源、尺寸、扫描修订合并。请求合并层只保留在途结果，持久缓存继续由原有缓存层管理。

日志写入线程的队列上限为 1024 条；普通日志过载时记录丢弃数量，错误与严重错误在队列不可用时写入单独的应急 JSONL 文件，写入失败时再输出到 stderr。每 64 条、250ms 空闲超时、严重日志或退出时刷出用户态缓冲；正常退出等待队列排空。这不是磁盘 `fsync` 保证，进程强制终止仍可能丢失最后的缓冲记录。

性能测量方法、结果与平台验证边界见[性能优化与验收](./性能优化与验收.md)。
